# Obsidian 学习插件：执行计划 v0.3（讨论稿）

日期：2026-09-10。依据：用户提供的 v0.2 计划书，以及文末官方文档核验。

本次范围是评审与计划，不包含创建插件仓库、安装依赖、运行 Claude 查询或修改现有 KnowledgeOps Agent 项目。

## 1. 先确定成功是什么

产品目标沿用 v0.2：阅读一份资料时，能在原地解决疑问，保留主线，之后接着学。

建议第一版的完成标准是一段真实流程：打开资料 → 选中不懂的文字 → 原地提问与追问 → 返回阅读 → 关闭并重开 Obsidian → 找回问题、答案和学习位置。

以下两点仍待用户决定，会影响阶段排序：

- 首要目标：解决自己的问题、求职作品，还是公开产品验证。若以求职为主，源码笔记和对照实验成为正式交付；若以自用为主，按需阅读，不把完整架构笔记设为开工条件。
- 主要资料：Markdown 或 PDF。下文按 Markdown 先做给出参考估算；如果日常主要看 PDF，应把 PDF 选区获取放到第一阶段，不能等到第八周才检验核心场景。

与 KnowledgeOps Agent 的优先级未定，因此本计划不承诺开工日期与固定周排期。

## 2. 对 v0.2 的关键调整

### 保留产品边界，缩短验证路径

保留独立插件、桌面端、Claude 首发、按资料组织主线、旁路提问、Markdown 学习记录。Codex、全库检索、文件修改和通用 Agent 能力继续延期。

先做贯穿界面和真实后端的最小闭环，再扩大源码学习和性能实验。终端脚本能跑通，不代表 Obsidian/Electron 内的 CLI 启动、取消和流式渲染能跑通，因此技术验证必须包含宿主内验证。

不要把“读完 Claudian、跑完其全部测试、写完架构笔记”当作开发前置依赖。锁定参考 commit，按当前问题阅读会话契约、运行时启动和编辑器集成三个路径即可。若选择求职优先，再单独安排深入学习。

### Quick Ask 的承诺是隔离，fork 是候选实现

官方 SDK 支持 `resume` 配合 `forkSession` 创建独立历史，但不保证每次分叉命中缓存，也不隔离文件系统。[来源 1]

用同模型、相近回答长度先比较两条路径：

- A：从主线已完成的轮次分叉，继承主线上下文。
- B：新建独立旁路会话，注入选区、所属段落和必要的主线摘要；后续追问只恢复这条旁路。

B 不采用“整份资料共用一个长期旁路会话”，避免无关疑问再次混在一起。没有主线时也必须可以 Quick Ask，不为一次查词强制启动主线。

先各做 5–10 个真实问题的探索性比较，发现上下文继承确实影响回答后，再扩大到每组 20–30 次。小样本结果只用于选方向，不用于宣称稳定的 P95 或成本收益。

若 B 的质量和延迟已满足实际阅读，先交付 B；只有 A 的上下文收益明显且运行稳定时，才将 fork 设为默认。小模型比较放在会话方案比较之后，避免同时改变模型与上下文而无法解释结果。

### 缓存与订阅额度分开评估

缓存按前缀匹配，并受有效期、最小长度等条件影响。工具定义变化和系统提示变化影响的层级不同，不能统一写成“配置变化导致全部缓存失效”。持久查询重启也不能直接证明服务端缓存失效。[来源 2]

记录 SDK 实际提供的输入、输出、缓存读取和缓存写入 token；缺失字段标为不可用。若这些字段按官方语义互斥，读取占比按 `读取 / (未缓存输入 + 缓存写入 + 缓存读取)` 计算，先核对锁定版本的返回结构。

订阅用量不能直接按 API 标价换算。现行官方帮助页说明相关用量仍计入订阅限制，但不据此承诺每次查询的精确额度。[来源 3] 第一版不做无法可靠测量的“本次消耗百分比”。

## 3. 第一版范围

| 必须交付 | 暂缓 |
| --- | --- |
| 快捷键提问、流式答案、停止、重试、追问 | 多模型与多后端切换 |
| 每份资料独立的主线，显式显示当前绑定资料 | 全 vault 检索、自动读全库 |
| Quick Ask 不写入主线 | 自动画像、掌握度打分 |
| 用户可编辑的疑问记录和恢复入口 | 多设备无缝恢复 CLI 会话 |
| 重命名、重启、切换资料后的正确恢复 | 通用 agent 工具、MCP 配置界面 |

“加入主线”、关联笔记自动绑定和丰富的讲解按钮放到基础闭环稳定之后。PDF 是否进入第一版由实际资料类型决定。

## 4. 开工前定下的设计

### 资料身份与跟随规则

用插件生成的 `studyUnitId` 表示学习单元，资料路径作为可更新属性，CLI 的 `sessionId` 作为可失效的后端引用。三者分离，避免路径重命名等同于资料换身份。

建议规则：

1. 用户首次点击“开始学习”或 Quick Ask 时创建学习单元，不因普通浏览自动建会话。
2. 切到已绑定资料或有效关联笔记时跟随切换；切到未绑定文件时保留当前主线，并明确标注其所属资料。
3. 固定当前主线后暂停自动跟随；提交消息时仍显示目标资料。
4. 关联笔记后续支持 `source: "[[资料路径]]"`，通过 Obsidian 链接解析定位；多个来源、循环引用或解析失败时提示选择，不猜测。
5. 捕获重命名事件更新路径；未捕获的离线移动或同步变化提供手动重新绑定入口，不承诺自动无损识别。

### 主线究竟知道哪些资料

第一版由插件构造上下文，不依赖 Agent 自行搜索整个 vault。

- Quick Ask：选区、标题路径、前后段落，以及用户问题；需要主线背景时附带限定长度的摘要或使用分叉。
- 主线：当前学习单元信息，加用户选定章节或片段。短资料可在明确的长度预算内完整加入；长资料显示实际带入范围，不默默截断后声称理解全文。
- 资料更新后，下一次提问刷新相关片段，保留旧问题当时的引用文本。资料中的指令按引用内容处理。

### 只读能力从配置开始

首版主线和旁路都不需要文件写入或命令执行；插件自身仅保存用户需要的学习记录。两条路径从开始就使用一致的最小工具配置，而不是先继承通用 Agent 的所有工具，再为保缓存增加权限绕行逻辑。

验证实际锁定版本的工具配置、设置加载、MCP 和 hooks 行为。不能仅靠 `canUseTool` 或提示词承诺只读：官方说明部分权限路径会在回调之前批准调用。[来源 4]

### 会话调度与故障恢复

- 每个主线一次只处理一个写入历史的请求；开始时固定 `studyUnitId`、`sessionId` 和 `requestId`。
- 切换文件不会改变已发出请求的归属；旧回复不能显示到新资料下面。
- 分叉基于已完成的主线轮次；若当前正在生成，排队等待完成，或明确选择独立旁路。
- 首版限制同时运行的旁路数量为 1；卸载插件时清理监听、界面和本插件启动的进程。
- SDK 报告成功或失败后都及时保存可用 session ID；启动失败与恢复失败分开处理。
- CLI 原始会话丢失时保留插件记录，允许用资料和摘要新开会话；明确这是重建上下文，不是原会话的完整恢复。
- 不自动重发状态不明的请求，以免重复计费或重复写入历史。

### 存储与定位

插件设置或 JSON 元数据保存版本号、学习单元身份、绑定关系和后端引用；vault 内专用可见文件夹保存 Markdown 学习记录。Markdown 是学习内容和复习状态的事实来源，不再维护一份独立可写的内容副本。

每条问题保留唯一 ID、资料身份、原选区、前后文、标题路径或 PDF 页码、问题、完整回答、时间及状态。摘要可以派生，不能替代完整答案。

定位时先使用位置提示，再用原文和前后文校验；匹配不唯一则显示原始引用并提示重新定位，不能跳到错误段落。用户编辑记录后重新读取；用户移除记录后不从缓存自动生成回来。删除学习记录不等于删除 CLI 自己维护的历史，界面和 README 应说明边界。

“加入主线”作为之后的显式操作：预览待加入的问题和回答，以带来源的消息追加到主线，而非宣称合并两条 SDK 历史。用问题 ID 记录状态，避免重复点击重复加入。

## 5. 最小架构

```text
src/
  main.ts                 插件生命周期、依赖组装
  core/                   领域类型、后端与存储接口
  application/            资料绑定、上下文构造、提问与恢复用例
  ui/                     主线面板、Quick Ask、记录入口
  adapters/
    obsidian/             选区、文件事件、链接解析、定位
    claude/               SDK、CLI 启动、流式事件、取消与恢复
    storage/              元数据与 Markdown 记录
tests/
```

`ui → application → core`；适配器实现 core 的接口，由 `main.ts` 注入。Obsidian API 限定在 UI、Obsidian 适配器和组合根；Claude SDK 不向上层泄露具体事件类型。

相比 v0.2，增加明确的用例层，是为了让会话归属、排队与恢复规则有归属，避免全部塞进 UI。暂不建立动态 provider 注册表、不创建空的 Codex 实现；定义最小的提问、恢复、取消接口，fork 作为可选能力即可。

选择 TypeScript、Obsidian 官方模板和现有构建工具链。配置 typecheck、lint、test、build；在 AGENTS.md 与 lint 中约束依赖边界。代码行数不是验收指标，以能否解释每层职责为准。

## 6. 分阶段执行

以下是 Markdown 首发的粗估，包含针对改动的验证，不包含熟悉 TypeScript 所需时间；首阶段后重估。按每周 10–15 小时约 4–9 周开发工作量，真实使用观察期可以与修复重叠，不承诺固定完成日。

| 阶段 | 预计投入 | 工作与交付 | 退出条件 |
| --- | --- | --- | --- |
| P0：验证后端与宿主 | 4–8 小时 | 锁定 CLI/SDK/Obsidian 版本；终端和 Obsidian 内均完成提问、流式接收、取消、指定会话恢复；小样本比较 A/B | 已登录的本机 CLI 可用；取消与恢复可解释；决定先落地哪条旁路路径 |
| P1：原地提问 | 8–12 小时 | 选区快照、快捷键、简单就近弹层、输入与流式答案、停止和重试；先支持一种 Markdown 视图模式 | 从选中文字到读完讲解可在编辑器完成；切换文件不串答案 |
| P2：主线与隔离 | 16–24 小时 | 主线面板、资料身份与绑定、明确的上下文范围、按 ID 恢复、独立旁路追问、请求调度 | 两份资料往返及重启后各自恢复；检查历史确认旁路未加入主线 |
| P3：留下学习成果 | 12–18 小时 | Markdown 完整记录、待复习状态、重命名更新、引用回跳、续学入口、记录编辑与移除后的刷新 | 真正关闭应用后仍能找回疑问；失效定位或会话丢失均有恢复入口 |
| P4：连续真实使用 | 10–16 小时，跨至少一周 | 完整学习一个章节；修复最影响阅读的故障；需要时增加加入主线、关联笔记或第二种视图 | 至少 3 次独立学习过程；核心故障用例通过；能说明它具体替代了哪一步旧流程 |
| P5：小范围试用 | 8–12 小时，反馈跨一至两周 | 测试安装包、示例 vault、README、演示；先邀请 3–5 位符合条件的试用者 | 获取主动再次使用、卡点和放弃原因；决定扩展或停止投入 |

Markdown 首发合计约 58–90 小时，属于规划估算，不能当作已验证工期。首次使用复杂度明显超预期时重新缩范围，而不是压缩测试和恢复处理。

如果 PDF 是核心资料：P0 就验证 PDF 选区、页码与上下文获取，P1 必须能在真实 PDF 上完成提问。PDF 适配初步另预留 16–30 小时，依据接口验证结果重估。句子级引用、扫描件 OCR 和截图自动注入继续延期；选区不可用时提供手动粘贴加页码，明确降级后的体验损失。

## 7. 验证与决策门槛

### 必须通过的回归场景

- 资料 A 提问过程中切到 B，A 的答案不进入 B 的界面或历史。
- 同一选区连续提问与取消，界面没有重复文本、悬挂状态或误归属记录。
- 主线历史中找不到旁路专用的唯一标记；该标记保留在旁路历史中。以真实历史检查为主，不能只问模型“你记得吗”。
- 资料重命名后仍归属原学习单元；离线改名无法定位时可重新绑定。
- 编辑选区附近内容后，记录正确定位或明确报无法定位。
- 重启插件可恢复；CLI 会话消失后学习记录仍能读，并提供重建入口。
- 用户修改或移除 Markdown 记录后，状态随之更新，不被后台覆盖或复活。
- CLI 未安装、未登录、超限、网络失败有清晰状态；错误后能重试。
- 确认所选运行配置下没有模型发起的文件修改、shell 或非预期工具执行。

测试分为纯逻辑单元测试、模拟后端事件的集成测试，以及少量真实 SDK/Obsidian 验证。缓存和 CLI 兼容性不能仅靠 mock 测试证明。首版仅声明已实际验证的操作系统和版本组合。

### 指标只服务于决定下一步

产品先看：一次阅读是否必须频繁切出、答案是否解决疑问、过几天能否继续、是否主动再次使用。问题次数多不一定更好，也可能是答案没说清楚。

技术先记：点击至首个可见内容、首个模型文本、完成耗时、错误与取消情况、可得的 token 用量。将冷启动与温启动、短与长上下文分开；对照实验保持问题、输出长度目标和网络条件尽量一致。

先不制定未经体验确认的硬性延迟秒数。P1 自用时确定“等待多久会打断阅读”，再作为后续取舍标准。任何串会话或误定位故障都优先于缓存优化。

小范围访谈只用于发现问题，不把 3–5 人的比例外推为市场结论。扩大到 v0.2 的 8–10 人时再评估其两周复用门槛。

## 8. 第一轮工作的明确清单

1. 确认首要目标、主要资料类型、每周投入与主项目优先级。
2. 选 2–3 份自己近期确实要学的资料，整理 10 个真实疑问作为验收样本。
3. 建立独立插件仓库与测试 vault，记录参考 Claudian commit，按问题阅读必要源码。
4. 完成 P0 的真实 SDK 与 Obsidian 验证，记录失败点、版本与原始数据。
5. 根据结果确定旁路方案和第一种支持的视图，开始 P1；不先投入全量架构复刻或大规模性能测试。

项目名、Codex 排期和商店发布无需阻塞上述工作。
